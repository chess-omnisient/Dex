Python, a widely used programming language for data scientists, offers a wide selection of libraries that you can install with the pip command, simplifying complex calculations and data analysis tasks. It also facilitates the automation of tasks and processes, streamlining workflows for enhanced productivity and efficiency.

Jupyter Notebook is an open-source web application that's become one of the go-to tools for data scientists, analysts, and even educators in recent years. It provides an environment where you can write live code, equations, visualizations, and narrative text - all in a single document, making it a versatile choice for a variety of data projects.

What sets Jupyter Notebook apart is its ability to combine code execution with data visualization and rich text, facilitating a more interactive and insightful data exploration process. You can jot down your thought process while simultaneously running code snippets, making it an excellent tool for both the development and sharing of data analyses.

Resources in Omnisient's AKS environment are allocated dynamically and managed by Kubernetes, which ensures efficient utilization of available resources while maintaining performance and scalability.

  1. Resource limits and requests - each project is allocated resources based on predefined minimum and maximum limits. The minimum (resource request) ensures each Jupyter instance has enough resources to start and run. The maximum (resource limit) prevents any single instance from consuming excessive resources, ensuring fair distribution across all users.

  2. Pod initialization - when a user opens a Jupyter instance, Kubernetes uses the defined resource requests and limits to create a new instance, known as a pod. A pod is a virtual environment that encapsulates the Jupyter application and its dependencies.

  3. Scaling mechanism -the AKS setup includes a single server and two scale set instances to handle varying workloads. When resource usage reaches a threshold, Kubernetes automatically provisions additional instances. When demand decreases, it scales down and frees up resources.

  4. Virtual server fit - each pod fits within the size constraints of the virtual server in use. Kubernetes continuously monitors resource usage and adjusts allocation to optimize performance.

  5. Resource monitoring and management - Kubernetes provides built-in mechanisms for monitoring usage and managing pod lifecycle, ensuring each Jupyter instance operates within defined resource limits without impacting overall system performance.

Working with your data in Jupyter

OmniHub reads data from the data warehouse into a Jupyter notebook, either from your own Data Preparation area or a project's shared tables. Queries are written as SQL strings and submitted through the omni_hub magic command; the result is a ResultSet object you convert to a pandas DataFrame with .DataFrame().

Viewing available tables

Before querying, load the extension and list the tables available to you:

  1. Load the extension:

    %load_ext omni_hub

  2. Return every table in a project:

    %omni_hub --list-tables

Querying data

Define the query as a SQL string, submit it through omni_hub, then convert the result to a DataFrame:

%load_ext omni_hub
data = %omni_hub {'select top 100 * from [project_code].[table_name]'}
df = data.DataFrame()
print(df)

  • Replace [project_code] with the project code, for example ClientName_Prj_00001. For Own Data Preparation, use ClientName_a.

  • Replace [table_name] with the table to query.

  • top 100 limits the extract to the first 100 rows. Remove it to pull the full table.

Queries use Microsoft SQL Server syntax, and can join a table against a partner's table within the same query – join on DW_ID_KEY or BestMatchID.

To identify a username for support queries or table-creation permission requests:

%omni_hub {'select current_user'}

The username is the long alphanumeric string ending in the project name.

💡 Tips for managing memory:

  • For large datasets, do as much data preparation, cleaning, joining, and sampling in SQL as possible before loading into the notebook – Python compute may run out of memory on very large datasets.

  • Load only the data needed – a filtered query over a full table pull.

  • Clear unused variables with Python's del, or restart the kernel to free memory between tasks.

Choosing a workspace size for a query

Query performance and processing time depend on the shape of the table being pulled, and the notebook's workspace size needs to match it.

  • A wide table (many columns, e.g. 500 columns across 3 million rows) is compute- and memory-intensive to process column-by-column, and typically needs the Extra Large workspace size.

  • A long table (few columns, e.g. 10 columns across 50 million rows) processes differently – the Large workspace size is typically sufficient.

👉 See Workspace size options above for the full CPU/memory breakdown of each workspace size.

⚠️ Pulling more data than a query actually needs increases the risk of the query timing out, independent of workspace size. Scope a query to the columns and rows actually needed rather than sizing up to compensate.

Optimizing memory for large tables

omni_hub returns a ResultSet object. Converting it directly to a DataFrame holds the data twice in memory – once as the ResultSet, once as the DataFrame – which can cause out-of-memory errors on large tables.

Export the ResultSet to CSV, delete it, then load the CSV into pandas instead. This holds only one copy at a time:

  1. Run the query with omni_hub.

  2. Save the result to CSV with .csv("path").

  3. Delete the original object with del.

  4. Load the CSV into pandas with pd.read_csv.

# 1) Run query via omni_hub
sql_query = "select top 10 * from [project_code].[table_name]"
rs = %omni_hub {sql_query}
df = rs.DataFrame()
print(df)
df.to_csv("my_table.csv", index=False)

# 2) Save to CSV
rs.csv("my_table.csv")

# 3) Delete the ResultSet to free memory
del rs

# 4) Read the CSV into pandas
import pandas as pd
df = pd.read_csv("my_table.csv", low_memory=False)

Writing a DataFrame back to a project

To write the results of an analysis back to the project tables, use omni_lab.

  1. Import the package:

    import omni_lab

  2. Copy the DataFrame back to the project:

    omni_lab.copy_to_project_tables(df, "PROJECT_CODE", "table_name")

  3. Replace PROJECT_CODE with your project code, for example QACOMPANYA_PRJ_00023, and table_name with a name of your choosing. Table names can't contain spaces.

The write runs asynchronously.

Virtual environments

A virtual environment (venv) is a persistent, isolated Python environment within a Jupyter project, separate from the project's shared Python installation. Packages installed inside a venv persist across sessions in the project's storage, avoiding the session-only installs and version drift that come with installing packages directly in the shared environment.

A venv is useful whenever a specific analysis or model needs a particular library version - for example, testing a newer release of a package without changing the version every other notebook in the project relies on. It also makes an analysis reproducible: recreating the same venv gives the same package versions, rather than whatever happens to be installed in the shared environment at the time.

Jupyter Notebook creates and activates project-specific venvs through the omni_helper extension.

Creating and activating a Venv

Run these two cells at the top of the notebook, every session:

  1. Load the omni_helper extension:

    %load_ext omni_helper

  2. Create and activate the venv:

    %omni_helper venv-activate <env_name>

    Replace <env_name> with any name you choose. The first time, this creates the venv and activates it; every time after, it just activates it.

Note: Initial creation takes 15 to 30 minutes. The venv itself persists in the project's storage, but a new session still needs to run both cells (%load_ext omni_helper and %omni_helper venv-activate venv) to reactivate it - reactivating an existing venv takes seconds.

💡 Use the same venv name across every notebook in the project, so each one activates the same persisted venv and the packages already installed in it.

Installing packages inside a Venv

Once a venv is active, install a package the same way as outside one:

!pip install <package_name>

Packages install from Omnisient's vetted package library. A package installed inside an active venv persists across sessions in the project's storage - install it once, and it's available every time that venv is reactivated, without installing it again.

👉 See Using Jupyter Notebook for Packages/Libraries Management for how package installs behave outside a venv.

⚠️ If a package isn't part of the vetted library, it isn't available to install this way. Contact support@omnisient.com to request it be added or updated.

Company Notebook Library

The Company Notebook Library allows analysts to share approved notebooks across your organization. Once a notebook has been reviewed and approved by the Omnisient team, it becomes available to all users within the company and can be copied into any project.

Accessing the library

The Notebook Library panel is available in the left sidebar within Jupyter. It displays all notebooks your organization has had approved.

To use a notebook, right-click it and select Copy into Project - a copy is added to your current project's file browser.

Promoting a notebook to the library

Any analyst can submit a notebook for inclusion in the Company Notebook Library.

⚠️ Clear your notebook outputs before submitting. Notebooks submitted with outputs will be declined. Before promoting, clear all outputs - go to Edit > Clear All Outputs, or Kernel > Restart Kernel and Clear All Outputs.

To submit a notebook:

  1. In the file browser, right-click the notebook you want to promote.

  2. Select Promote to Library.

  3. A confirmation modal appears - review and confirm your submission.

  4. Your submission has been logged, and the Omnisient team has been notified to begin the review process.

What happens next

Once submitted, your notebook enters a review queue. The Omnisient team will review it and communicate the outcome by email.

  • Approved - the notebook is added to your organization's library and becomes visible to all users in the Notebook Library panel.

  • Declined - you will receive an email with the reason for the decline. Review the feedback, make the necessary changes, and resubmit.

Sharing a notebook with a project member

To share directly with a specific project member, use omni_helper.

Permissions required: Active participant in the project.

Prerequisites: Jupyter Notebook open within your project.

Step 1: Load the extension

%load_ext omni_helper

Step 2: Get the recipient's user address

Run omni_helper project-members to return a list of project members and their user addresses. Copy the User Address of the intended recipient.

💡 User addresses are project-specific - the same user has a different address in each project they belong to.

Step 3: Send the file

omni_helper send-files --paths [filename.ipynb] --receiver [user_address]

💡 Filenames cannot contain spaces. Rename the file before transferring if needed.

Step 4: Check transfer status

Run omni_helper transfer-history and match the output against the REQUEST_ID returned when you submitted.

Recipient: The file appears in a shared folder within their Jupyter workspace inside a dated subfolder. There is no automatic notification - they will need to check manually.
