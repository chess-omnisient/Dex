# Feature Alert (Internal Sales & Accounts)

Generate a Slack-ready internal alert to brief the sales and account management team on new features or product updates. This is the internal-facing counterpart to the client newsletter — more detailed, more direct, and focused on enabling conversations rather than client communication.

**Audience:** Sales, account managers, customer success
**Tone:** Direct, informative, practical — written for people who need to explain this feature to clients confidently, quickly

---

## How feature alerts are structured

A feature alert is a single message covering one release (which may include multiple features). It contains:

1. **Header** — sprint or release name + emoji headline of features shipped
2. **What's new** — plain description of each feature or change (per feature if multiple), with the relevant KB article linked inline under the feature using the link format below
3. **Caveats** — placed inline under the feature they apply to (not at the bottom). Only include if genuinely needed.
4. **Talking points + objection handling** — per feature: anticipated client questions with concise approved responses
5. **Closing sign-off** — brief, friendly close inviting questions

**No client-ready one-liners section.** Talking points are written conversationally and serve double duty for async comms.

**KB article placement:** Link articles inline under the relevant feature. If a feature has multiple KB articles, list them each on their own line. If a feature has no article yet, skip — don't flag it. For features with several related articles (e.g. activation), use a "Knowledge base refreshers:" subheading before listing them.

---

## Alert format

```
What's new - [Sprint / Release Name]
[Feature 1] · [Feature 2] · [Feature 3]


[Feature 1 name]

[2–3 sentences. What it does, how it works, what it changes. No marketing language — just clear description.]

[KB article link if available]


[Feature 2 name]

[Same format.]

[KB article link if available]

[Inline caveat — only if this feature has a specific gotcha the team needs to know.]


[Feature 3 name — if multiple KB articles]

[Description.]

Knowledge base refreshers:
[Article 1 link]
[Article 2 link]
[Article 3 link]


Talking points

- [Feature name]
  "[Anticipated client question]" [Short, accurate response. 1–2 sentences max.]
  "[Anticipated client question]" [Response.]

- [Feature name]
  "[Anticipated client question]" [Response.]


Let me know if you have any questions or require additional guidance.
```

---

## What to gather before writing

1. **What shipped?** — list all features or changes in this release
2. **Why does it matter to clients?** — the business value (saves time, reduces errors, unlocks something)
3. **Intercom KB article(s)** — links to all new or updated articles for this release
4. **Anything the team needs to know?** — plan gating, setup requirements, known edge cases, phased rollouts
5. **Anticipated client questions or concerns?** — data security, edge cases, potential confusion
6. **Who's this most relevant for?** (optional) — specific client segments, verticals, or use cases

If a client-facing newsletter already exists for this release, use it as context — extract the feature description and "why it matters" to stay consistent. Don't duplicate client-facing language verbatim; translate it into internal-facing directness.

---

## Optional: Targeting guidance

If meaningful targeting guidance can be given, add after the talking points:

```
Who to reach out to proactively
[1–2 sentences describing which client types, segments, or accounts would benefit most.]
```

Skip if it applies broadly to all clients.

---

## Tone rules

- Talking points are structured as objection handling only — no framing preamble. The objection response IS the talking point.
- Objection responses should be accurate and concise — not defensive. If something is genuinely limited, say so clearly.
- Don't repeat the KB article descriptions — talking points are for conversations, not documentation.
- Keep the whole message scannable — AMs will read this quickly before jumping on a call.
- No client-ready one-liners section. Talking points written well are already paste-able.

## Caveat rules

- Place caveats inline under the specific feature they apply to — not in a separate section at the bottom.
- Only include if there's something the team genuinely needs to know before talking to clients (e.g. manual process, phased rollout, potential client confusion).
- Do not use for general commentary.
- If plan gating applies, state the plan name specifically.
