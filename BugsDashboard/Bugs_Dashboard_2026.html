Contracted SLA clients, Platform / API split and credit exposure

Airvantage and FNB hold the contracted support SLA set out in the targets table above, with defined response and resolution windows and optional paid after-hours cover. FNB additionally holds the separate API SLA, which carries stricter resolution times and service credits payable on breach at Sev 1 or Sev 2. The Severity Classification Guide separates Platform issues (the web application: UI, projects, uploads via Desktop or Server Connect, reports, user management) from API issues (online scoring APIs, batch data APIs, or any programmatic interface a client's systems call directly). Every tracked item this period is classified against that rule.

Data source and scope – Tiers 1 and 2 come from ClickUp list 901211098087 (Omnisient > Bugs > Bugs Board). Tier 3 comes from list 901216071368 (Notice board). Tier 4 comes from list 901218011842 (Platform Support) plus non-bug tagged tickets on the Bugs Board. Tiers 1 to 3 cover 1–29 September 2026 in SAST, data pulled on 29 September; Tier 4 covers 1 July to 29 September, because September alone held one genuine support request. This dashboard deliberately counts the Bugs Board only; Bug-type tasks also exist in Intake Console and the Platform Development sprints and are not included here.

Support request exclusions – 11 tasks fell inside the quarterly window. Removed: 2 test tickets raised from an internal address with bodies reading "test" and "chess"; 2 duplicates, being the second of two pairs created under a minute apart from the same Intercom conversation; and 1 internal coordination task already counted in the Tier 1 and Tier 2 figures, which would otherwise be double counted. Two of the remaining six were raised from internal addresses rather than by a client, so their end client is shown as N/A. The closed auto-logout request shares its underlying cause with the auto-logout bug in Tier 2 but is a separate Intercom conversation, so it is counted in both tiers.

* Resolution time – Business-days figures apply Omnisient support hours (09:00–17:00 SAST, weekdays). The Error saving notebook on SBSASRX profile ticket shows a 70-calendar-day gap between creation and its recorded close with no explanation in the thread, which likely reflects a bulk status update rather than active work. It is counted in ticket totals but excluded from Average Time to Resolve, pending confirmation from the assignee.

† Close dates are partly administrative, and resolution times are upper bounds – Two support tickets were closed in ClickUp within 21 minutes of each other on the morning of 28 September, which is a board-clearing sweep rather than two resolutions. One of them is the broken ACE report, confirmed as actually resolved on 4 September; its title records the fix as already applied when it was logged. This dashboard uses the real resolution date where it is known and ClickUp's timestamp otherwise, so any figure resting on a ClickUp close date should be read as an upper bound. The notebook-promotion bug shows the same pattern in reverse: a workaround confirmed with the requester on 21 September, then reopened on 28 September because no permanent fix had been implemented.

Why some closed tickets show no resolution date – ClickUp only stamps a close date for statuses of type "closed". The board's "done" status is not one, so tickets sitting in "done" never receive a close timestamp, and the Resolution Date field is unset on all of them. One customer ticket sits in that position here – the ABSA "Unable to View Team's Projects and Datasets" ticket. Its resolution time is taken from the ClickUp status-change event that moved it to "done" (4 September, 34 minutes after creation) and is marked † in the table, because a status change is an administrative timestamp rather than a confirmed fix time. On that basis it is counted in totals and included in Average Time to Resolve. A further 12 bug tickets created between June and August sit in "done" with no close date and are excluded from this month's figures entirely, pending a data-hygiene pass.

Severity is unreliable, and this undermines every SLA figure on this page – The Severity Classification Guide states that every Intercom ticket defaults to Sev 3 and instructs the support team to actively set severity before converting a conversation, warning that leaving the default "may underclassify urgent issues and breach SLA windows". All 11 customer tickets here sit at Sev 3, which is consistent with the default never being changed rather than with deliberate triage. Because severity determines which resolution window applies, any ticket that should have been Sev 1 or Sev 2 is being measured against a 3-business-day target instead of 8 or 24 hours, so the breaches reported here are a floor, not a full count. The guide also notes that an automated Bug Severity Classifier will not override a severity already set by a person, so an unset severity stays at the default permanently.

Platform versus API, and service-credit exposure – The guide distinguishes Platform issues from API issues. The separate API SLA, with stricter resolution times and service credits payable on breach, applies to FNB; API issues at Sev 1 or Sev 2 carry that credit exposure. No FNB ticket falls inside this reporting window, so no breach reported here carries service-credit exposure. That is a property of this particular month rather than a structural safeguard: FNB tickets do exist immediately outside the window, including an OmniCheck alert titled "FNB Features API Has Failed" that closed in late August, which is precisely the category that would be exposed. This dashboard does not yet capture the Platform/API split as a field, so in a month where FNB does raise a ticket it could not currently distinguish an exposed breach from an unexposed one.

Recorded root causes – The Resolution field is populated on only 2 of the 11 customer tickets. Four others are fully closed with a confirmed close date but no recorded root cause (the data preparation failure, the SQLPad access issue, the SBSASRX notebook save and the auto-logout issue), so what went wrong on those is not captured anywhere in the ticket.

Client attribution – ClickUp's "Client" custom field holds the first name of whoever opened the Intercom conversation, which is frequently an Omnisient staff member logging on a customer's behalf rather than the customer. Verified example: the Shoprite_PRJ_00146 export failure carries Client "Sharon" with User Email sharon@omnisient.com. Clients shown here were therefore derived from ticket titles, embedded project codes (ABSA_PRJ_00038, SHOPRITE_PRJ_00461) and requester email domains instead. One ticket's client could not be confirmed and is shown as N/A pending AM follow-up.

Tier 1 average time to close – Calculated per task from ClickUp creation and close timestamps across the 51 tasks that carry both. The 6 tasks in "done" status are excluded because all 6 have a null close date, as are the 13 still open and the 1 triaged out. Business-days figures apply Omnisient support hours (09:00–17:00 SAST, weekdays); the calendar-day figure is shown alongside because the monthly board report uses that basis. Nine tasks share two bulk-close timestamps, which are likely batch closures rather than individual resolutions; excluding them moves the average only from 2.27 to 2.31 business days, so they are left in.

SLA targets are verified against the contractual schedule – The resolution windows used throughout (8 hours, 24 hours, 3 working days, 5 working days) match the Call Priority and Response Times table exactly, so every resolution figure on this page is measured against the contractual target. Support hours of 09:00 to 17:00 CAT, Monday to Friday, also match the business-hours basis used in every calculation here; CAT is UTC+2, the same offset as SAST. Response targets (1, 4, 24 and 48 hours by severity) are now documented and shown in the targets table, but response attainment is still not measured because ClickUp captures no first-response timestamp. A task to build that measurement exists and has not started, so the response half of the SLA remains unreportable rather than unmet.

Known gap – The Bug Duplicate and Non-bug lists also hold September PROD alerts that have not been exhaustively counted, so the true cross-list PROD alert total exceeds 306.
